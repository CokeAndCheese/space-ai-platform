## 3. 决策与汇报关系

- 用户只处理产品方向、范围、重大架构取舍、风险接受、人员变动和发布决策。
- 产品经理吸收日常研发协调；获批后自行拆解、分工、排序和组织验收。
- 研发人员不绕过产品经理向用户汇报日常技术细节；遇到超出授权的重大风险时提交产品经理升级。
- 技术负责人提供架构裁决建议，但产品范围和最终验收仍由产品经理管理。
- QA 独立于实现人员，发布结论不能只依赖开发者自测。
- 团队编制不因单工作区而变化；研发执行改为产品经理控制的单一写入队列。读-only 审查可并行，代码写入必须串行交接。

## 5. 组织变更触发条件

出现以下任一情况时，产品经理必须立即更新本文件：

- 新增或撤销岗位/人员任务。
- 一个岗位拆成多个专业分工，或多个岗位合并。
- 核心职责、文件所有权或系统边界发生迁移。
- 汇报关系、决策权或验收权发生变化。
- 临时项目组、专项负责人或阶段性角色被设立或结束。

## 6. 变更流程

```text
识别组织优化机会
→ 在“提议中变更”记录方案、原因、影响和成本
→ 向用户汇报并请求所需决策
→ 用户批准
→ 调整人员任务、名称、职责和汇报关系
→ 更新“当前生效架构”与 PRODUCT_CONTEXT
→ 追加 DECISION_LOG
→ 向用户反馈完整最新组织架构
```

未获批准的提议不得写入“当前生效架构”。废止的结构通过决策日志追溯，不在本文件中长期堆积。
